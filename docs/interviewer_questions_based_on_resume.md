## 3. Paper Research Agent 项目总览问题

### Q5：你这个项目整体是做什么的？

建议回答：

```text
这个项目是一个面向论文调研的 Tool-Using Agent。用户输入一个研究主题后，系统会自动调用多个论文检索工具，比如 arXiv、Semantic Scholar 和 OpenAlex，获取真实论文元数据。

然后系统会统一不同来源的数据结构，保存 papers.json，尝试下载 PDF 并解析正文，如果 PDF 不可用就退回摘要抽取证据。最后生成 evidence.json 和 Markdown 综述 report.md。如果选择 DeepSeek 模式，还会把论文和证据交给 DeepSeek 生成更自然的中文综述。
```

### Q6：这个项目为什么算 Agent，而不只是普通脚本？

建议回答：

```text
它不是单步脚本，而是围绕论文综述这个目标执行多步任务。它会调用多个外部工具，保存中间状态，处理工具失败，并最终生成可追溯结果。

具体来说，它包含工具调用、多源检索、状态落盘、异常恢复、LLM 写作和输出评测，这些都是 Agent 工程中常见的组成部分。
```

### Q7：这个项目的输入和输出是什么？

回答：

```text
输入是研究主题、论文数量、证据数量、检索源和写作方式。

输出主要有三个：

papers.json：保存检索到的论文元数据。
evidence.json：保存从论文正文或摘要中抽取的证据。
report.md：最终生成的 Markdown 综述报告。
```

### Q8：你这个项目最核心的技术难点是什么？

建议回答：

```text
最核心的难点不是调用 DeepSeek，而是让真实论文检索链路稳定。

一开始只接 arXiv，但实际运行中出现了 429、503、timeout。后来我改成多源检索，接入 Semantic Scholar 和 OpenAlex，并设计统一 Paper 数据模型。这样即使一个源失败，也能继续尝试其他来源。

第二个难点是降低 LLM 幻觉，所以我设计为先检索真实论文和证据，再让 DeepSeek 基于 evidence 写作。
```

## 4. 多源检索相关问题

### Q9：为什么要接 arXiv、Semantic Scholar、OpenAlex 三个源？

建议回答：

```text
因为单一数据源不稳定，而且覆盖范围不同。

arXiv 适合预印本和 PDF 获取，但容易限流。
Semantic Scholar 有 citationCount、externalIds 和 openAccessPdf，适合学术元数据。
OpenAlex 覆盖面广，开放数据比较友好，也有引用数和机构等信息。

多源检索可以提高覆盖率和鲁棒性。
```

### Q10：三个源的数据格式不同，你怎么统一？

建议回答：

```text
我定义了统一的 Paper 数据模型，包括 arxiv_id、title、authors、summary、published、updated、pdf_url、page_url、source、citation_count。

每个数据源都有自己的 client，负责把 API 返回结果转换成 Paper 对象。这样后面的 pipeline、证据抽取和报告生成都只处理统一模型，不关心具体来源。
```

### Q11：你如何做多源去重？

建议回答：

```text
目前主要按标题归一化去重，把标题转小写并清理多余空白后作为 key。如果多个来源返回同一标题，就融合元数据。

融合时保留更完整的摘要、PDF 链接、页面链接，并取更高的 citation_count。
```

如果继续追问缺点：

```text
标题去重是 MVP 方案，可能误合并或漏合并。后续应该结合 DOI、arXiv ID、Semantic Scholar externalIds、OpenAlex ID 做更准确的去重。
```

### Q12：Semantic Scholar 429 怎么处理？

建议回答：

```text
Semantic Scholar 匿名接口容易限流。我做了等待和重试，同时支持从 .env 读取 SEMANTIC_SCHOLAR_API_KEY。

如果仍然 429，可以提高等待时间、减少请求量、申请 API Key，或者使用 OpenAlex 作为替代源。
```

### Q13：OpenAlex 的 abstract_inverted_index 是什么？你怎么处理？

建议回答：

```text
OpenAlex 的摘要不是普通字符串，而是倒排索引。它的格式大概是每个词对应出现位置列表。

我遍历每个 word 和 positions，把它们转换成 (position, word)，再按 position 排序，最后拼接成普通摘要文本。
```

### Q14：如果三个源都失败怎么办？

建议回答：

```text
当前系统会明确报错，提示所有论文检索源都没有返回结果。

如果生产化，我会进一步记录每个源失败原因，提供更清晰的用户提示，比如 arXiv 限流、Semantic Scholar 需要 API Key、OpenAlex 网络不可达等。
```

## 5. Agent / RAG / LLM 专项问题

### Q15：Agent 和普通 LLM 应用有什么区别？

回答：

```text
普通 LLM 应用通常是一次输入一次输出。Agent 会围绕目标进行多步执行，包括任务拆解、工具调用、观察结果、更新状态和生成最终结果。
```

结合项目：

```text
我的项目会调用论文检索 API、PDF 解析器和 DeepSeek，不是直接让模型回答。
```

### Q16：你的项目和 RAG 有什么关系？

回答：

```text
它有 RAG 思想。RAG 是先检索外部知识，再增强模型生成。我的项目先检索论文和证据，再让 DeepSeek 基于这些证据生成综述。

不过它还不是完整向量 RAG，因为目前证据抽取主要是关键词匹配，还没有 embedding 和向量数据库。
```

### Q17：如果要升级成标准 RAG，你会怎么做？

回答：

```text
我会把 PDF 正文切成 chunk，对每个 chunk 做 embedding，存入向量数据库。用户输入主题后，先检索最相关的 chunk，再进行 rerank，最后把 top evidence 输入给 LLM 生成综述。

同时保留论文 ID 和页码，保证引用可追溯。
```

### Q18：DeepSeek 在你的项目里扮演什么角色？

回答：

```text
DeepSeek 是写作增强模块，不是事实来源。

事实来源是 arXiv、Semantic Scholar、OpenAlex 返回的论文，以及从 PDF 或摘要中抽取的 evidence。DeepSeek 只基于这些结构化材料生成更自然的 Markdown 综述。
```

### Q19：怎么降低 DeepSeek 幻觉？

回答：

```text
第一，不让 DeepSeek 直接根据主题写，而是输入 papers.json 和 evidence.json。

第二，system prompt 要求只能依据提供的论文和证据写作。

第三，要求关键结论带论文 ID 引用。

第四，后续可以加验证模块，检查报告里的引用是否存在于 papers.json。
```

### Q20：什么是 evidence-first 设计？

回答：

```text
evidence-first 是先收集证据，再生成结论，而不是先让模型生成结论。

我的项目先检索论文，抽取 evidence，再生成报告。这样生成内容有依据，也方便追溯。
```

### Q21：你的 Agent 有没有 memory？

回答：

```text
有外部状态型 memory。papers.json 保存检索结果，evidence.json 保存证据，report.md 保存最终结果，.cache 保存 arXiv 查询缓存。

这些中间状态让后续写作、评测和调试都可以复用。
```

### Q22：如果让 Agent 自主规划，你会怎么改？

回答：

```text
当前是规则式 pipeline。后续可以加入 LLM Planner，让模型先生成调研计划，比如先查综述论文，再查高引用论文，再查最新论文。

还可以加入 Reflection，让模型检查证据是否足够，不足时自动二次检索。
```

## 8. 算法与基础知识可能提问

### Q34：标题去重为什么可能有问题？

回答：

```text
因为不同论文可能标题很相似，但不是同一篇；同一篇论文在不同来源中标题也可能有细微差异。

所以标题去重简单但不完美。更好的方式是结合 DOI、arXiv ID、Semantic Scholar externalIds、OpenAlex ID。
```

### Q35：关键词匹配和向量检索有什么区别？

回答：

```text
关键词匹配只能匹配字面词，简单快，但不能理解语义。

向量检索可以把文本映射到语义空间，找到表达不同但语义相近的内容，更适合复杂问题。
```

### Q36：BM25 和 embedding 检索有什么区别？

回答：

```text
BM25 是基于词频和逆文档频率的稀疏检索，适合关键词明确的场景。

Embedding 检索是稠密向量检索，适合理解语义相似度。

实际 RAG 系统中可以结合两者做 hybrid search。
```

### Q37：什么是 rerank？

回答：

```text
rerank 是在初步检索出一批候选结果后，用更精细的模型重新排序。

比如先用 BM25 或向量检索找 top 50，再用 cross-encoder 或 LLM 判断 query 和文档的相关性，选 top 5 给模型。
```

## 9. 场景设计题

```text

```

### Q39：如果让你做一个“医学文献 Agent”，你会怎么做？

结合你的本科背景：

```text
可以接入 PubMed、ClinicalTrials、医学指南数据库。检索结果统一成医学文献模型。证据抽取要保留 PMID、研究类型、样本量、结论等字段。

生成时必须强调不能替代医生诊断，并对证据等级做区分。
```

### Q40：如果用户问一个非常模糊的问题，比如“MCP”，怎么办？

回答：

```text
MCP 是缩写，可能有多种含义。Agent 应该先做 query disambiguation，可以让 LLM 生成候选解释，或者反问用户确认。

例如 MCP 可能是 Model Context Protocol，也可能是其他领域术语。确认后再检索会更准确。
```

## 12. 最建议你重点背熟的 8 个回答

### 1. 项目介绍

```text
这是一个面向论文调研的 Tool-Using Agent，能调用多个论文源检索论文，抽取证据，并用规则式或 DeepSeek 生成可追溯综述。
```

### 2. 为什么是 Agent

```text
因为它有多步流程、多工具调用、状态落盘、异常恢复和结果评测，不是单轮问答。
```

### 3. 为什么多源检索

```text
因为 arXiv 等单源不稳定，多源可以提高覆盖率和鲁棒性。
```

### 4. 怎么降低幻觉

```text
先检索真实论文和 evidence，再让 DeepSeek 基于 evidence 写作，并要求绑定论文 ID。
```

### 5. 最大难点

```text
真实外部 API 不稳定，比如 arXiv 429/503、Semantic Scholar 429，所以我做了重试、缓存和多源切换。
```

### 6. 最大不足

```text
证据抽取还停留在关键词匹配，后续要加 embedding、向量库和 reranker。
```

### 7. 如何生产化

```text
改成 FastAPI + 异步任务队列 + 数据库 + 缓存 + 日志监控 + API 限流。
```

### 8. 和传统项目相比亮点

```text
传统项目多是固定输入输出，而这个项目是围绕目标自动调用多个工具、处理失败、保存状态并生成可追溯结果的 Agent 工作流。
```
